## Description
## Symptom

v0.7.0 tightens at least four gate rules in ways that turn a v0.6.11 design-green corpus into 163
blocking findings. The CHANGELOG has no Compatibility or migration section, and three of the four
tightenings are not mentioned at all. docs/release-notes.md rule 3 requires exactly that section
"whenever a release changes schemas, installation receipts, attestations, registries, or CLI
behavior: what still works unchanged, what is rejected now, and the exact commands to migrate."

## Reproduction

Same design (H2, /Users/ramirosalas/workspace/H2 at c59bc81), same tree, two binaries:

```
$ machinery check design                                   # v0.6.11
0 blocking (ERROR/DRIFT) finding(s)
design-green: all applicable design gates green
$ echo $?
0

$ machinery check design                                   # v0.7.0
163 blocking (ERROR/DRIFT) finding(s)
$ echo $?
1
```

Same result with the CI invocation `machinery check design --commit <sha> --warnings-as-errors`:
v0.6.11 exit 0, v0.7.0 exit 1.

## The four tightenings and their documentation status

| Finding class | Count | In CHANGELOG 0.7.0? |
|---|---|---|
| Gx-trace: no per-consumer READS declaration for an event-contract edge | 61 | Yes: "Event-contract consumer `reads` bind per edge" (one line, no migration steps, no mention that existing shared declarations become errors) |
| Gx-trace: legacy READS has ambiguous consumer ownership | 28 | Same line |
| Gx-trace: expected exactly one complete READS per row / conflicting READS | 10 | No |
| Gx-trace: empty or malformed READS field (multi-word names) | 19 | No (see MAC-wcrd) |
| Gd-idcite: owning oracle has no transition governed by this guard | 31 | No |
| Gd-idcite: malformed CLAUSES declaration (prose over-match) | 13 | No (see MAC-3iga) |
| Gv-attest: GV_MISSING_IMPLEMENTATION_SUBJECT on a legacy design-only behavioral claim | 1 | Yes: "Attestation evidence v2 kinds" |

The single documented Gx line does not convey that a design whose consumers shared one declaration
per event now needs one declaration per (event, consumer) edge, nor what the migration is.

`Gd-idcite: owning oracle has no transition governed by this guard` is the one with real semantic
weight: it is a new obligation that a guard declaring CLAUSES must gate at least one transition in
its OWN oracle. In the reproducing design 31 guards fail it, and spot checks confirm the guards
genuinely appear in no oracle (for example `guardFeedbackAttributed`, `guardStewardMayWrite`,
`guardPackIsPureConfig`, `guardApprovalAttributed`: `grep -rl` over design/machines/*.oracle.md
returns nothing). Whether a guard that gates a creation action rather than a state transition
should be exempt is a design question the release note never posed.

## Also undocumented: the regeneration stamp

Upgrading forces a full regeneration. On the reproducing design that is 254 files
(83 .tla, 83 .cfg, 85 .oracle.md, 3 .als), each a single line
`machinery-version: v0.6.11` -> `v0.7.0`, no content change. That is the good case and the design
handles it as a stamp-only commit, but the CHANGELOG does not say which artifact families are
restamped or confirm that nothing else moves. docs/release-notes.md rule 1 asks for exactly that.

## Ask

Add the Compatibility and migration section: per tightened gate, what is now rejected, one worked
before/after example, and the regeneration/migration commands. State whether the Gd guard-ownership
rule is intended to cover creation guards.

## H2 impact

BLOCKER for planning. H2 pins v0.6.11 in CI and treats a machinery upgrade as its own stamp-only PR
(.github/workflows/design-check.yml:33-35, design/BUILD.md section 10). Without a migration section
H2 has to reverse-engineer 163 findings into a work plan by hand, which is what this assessment had
to do.
