# crm: the reference project

A small CRM (deals, tasks, an audit trail) built with machinery v2 from the design up: a Go HTTP
service on a real Postgres. The design lives in `design/` and `contracts/`; `design/gen/` is
generated by `machinery gen` and never edited. `design/owed.yaml` lists everything not proven
yet. The service takes every transition from the generated tables (`internal/fsm` drives them;
`internal/api` implements the named guards, actions and actors). Tables are read from
`MACHINERY_TABLES_DIR` when set, else `CRM_TABLES_DIR`, else `design/gen/tables`; a table that
names a unit the service does not implement stops it at start.

## Commands

| Command | Does |
|---|---|
| `make` | Lists the targets. |
| `make up` | Starts Postgres 17 (container `machinery-crm-pg`, empty on every start) and waits until healthy. |
| `make serve` | Builds `.bin/crm` and runs it against that database; the UI is at `http://127.0.0.1:18080/`. |
| `make e2e` | The end-to-end suite: the real binary over HTTP against the real Postgres. Needs `make up`. |
| `make check` | gofmt, `go vet`, `machinery check`. |
| `make evidence` | The suite through `machinery run`: a receipts file for the current commit. |
| `make verify` | The end gate: `machinery landing --base $(BASE) --probe` (check with the ratchet, the formal tools re-run against the committed results, the whole suite once through `run`, `verify`, the probe). `BASE` is the ref the change started from (default `HEAD~1`); it must contain this project. |
| `make formal` | `machinery formal gen --check`, then `machinery formal check`: TLC and Alloy for real (needs Java; `FORMAL_WORKERS`, default 2). |
| `make demo-pm` | The planner's loop on a throwaway copy with its own bd backlog (`demo/pm.sh`; needs `make up`). |
| `make probe` | `machinery probe`: mutates every proven transition in the tables the service reads and expects the suite to notice (`MAX=n` keeps the first n). |
| `make psql` | A psql shell as the admin role. |
| `make down` | Stops Postgres and removes the container and its data. |

`MACHINERY_TOOLS` names the directory of the pinned tools (modelith, xstate, the formal jars); it
defaults to the repository's `.bin`, where `machinery` itself is expected too (`make build` at the
root). `DEMO.md` walks through all of it, one command at a time.

## Ports and configuration

- Postgres: `127.0.0.1:15432`, database `crm`, admin role `crm_admin` (migrations only), app
  role `crm_app` (the service).
- Service: `CRM_ADDR` (default `127.0.0.1:18080`), `CRM_DATABASE_URL`, `CRM_ADMIN_DATABASE_URL`.
- `GET /healthz`: 200 `{"status":"ok"}`, or 503 `{"code":"STORE_UNAVAILABLE","message":"..."}`.

## Identity

The caller is named by the `X-User-Id` header: a missing, malformed or unknown id is 401. This is
enough for an example and is not authentication: anyone who can reach the service can name any
user. Do not use it in production.

## The UI

`make serve`, then open `http://127.0.0.1:18080/`. The pages are rendered by the service itself
(`internal/api/web.go`, `internal/api/web/`: standard library templates, embedded in the binary,
no script, no build step, no external URL). Choose a user (or create one), then create deals and
tasks and press the buttons of their events. Every button posts a form to `/ui/...`, which sends
the same request an API client would send, as the selected user, through the same routes: a click
takes the transition path of the API and nothing else. A refusal shows its code and message next
to the record (`refusal-<id>`); effects an answer lists as `simulated` would show as a note
(`simulated-<id>`), and none are left. The audit trail is at the bottom. The UI has no
operations of its own, so the design and the OpenAPI contract are unchanged.

## The suite and the owed list

`e2e/transitions_test.go` walks the committed tables (`design/gen/tables`, never
`MACHINERY_TABLES_DIR`): one subtest per transition, ignore and clause case, which arranges a
record in the source state, fires the event over HTTP, checks the answer and the row, and claims
only the effects it observed (each audit effect as exactly one audit row). The `onError` and `after` cases
are induced on the real database by the hooks of `failure_test.go`: INSERT on `deal_wins` revoked
from `crm_app`, and an ACCESS EXCLUSIVE lock on it held past the `closeTimeout` deadline.
`failure_test.go` also pauses the container (`docker pause machinery-crm-pg`, always unpaused in a
cleanup) to prove that a database that does not answer yields 503 `STORE_UNAVAILABLE` within three
seconds. These tests change the database for every client, so no test of the suite runs in
parallel. `audit_test.go`, `adversary_test.go`, `single_writer_test.go` and `scenarios_test.go`
prove the invariants, the abuse failure modes and the scenarios.
`scenario_win_test.go` walks two scenarios again in a real headless Chrome (chromedp, helpers in
`browser_test.go`): `sc:rep-qualifies-and-wins-a-deal` is proven by `TestScenarioRepQualifiesAndWins`
(HTTP) and `TestScenarioRepQualifiesAndWinsInBrowser`, `sc:rep-cannot-change-another-rep-s-deal` by
`TestScenarioRepCannotChangeAnotherRepsDeal` (HTTP) and `TestUIRefusalShown`; each emits its own
receipt. The browser is `CRM_CHROME` when set, else Google Chrome at its macOS path, else
`chromium` or `google-chrome` on PATH; without one these tests fail and say to set `CRM_CHROME`.
Each test starts one browser and closes it when it ends. The suite honors `MACHINERY_ONLY`; under `machinery probe` it runs only the
subtest of `MACHINERY_PROBE_CASE`.

After a change: `make up`, `make evidence`, `machinery owed sync --prune-only`, commit,
`machinery verify`. `machinery owed list` says what is still unproven and why.

## Probing the tests

```
make probe        # machinery probe -- env GOMAXPROCS=2 go test ./e2e/... -count=1 -p 1
```

`machinery probe` copies the committed tables, changes one proven transition (`retarget`: another
target state; `drop-effect`: its first action removed), points the service at the copy with
`MACHINERY_TABLES_DIR` and runs the suite once per mutation. The tests keep reading the committed
tables, and `probe_filter_test.go` runs only the subtest of `MACHINERY_PROBE_CASE`, so one run
takes about a second. A mutation is killed when that case is no longer proven. A survivor means a
test that claims what it did not look at, or a path in the service that does not go through its
table: fix the test (or the service), never the probe.

Last result: `checked: 33 mutations, 33 killed, 0 survived` (12 `retarget`, 21 `drop-effect`: every
transition case of both tables, the `onError` and `after` cases of `closing` included).

## Formal models

The two critical areas of `design/risk.yaml` have formal models in `design/formal/`
(`docs/formal.md` in the repository is the working order). `Deal.tla` and `crm.als` are generated
by `machinery formal gen`; the properties and the manifests are written by hand; results,
`baseline.json` and `traces/` are written by `machinery formal check` and `machinery formal
baseline` and committed.

- `deal-win` (TLA+, `concurrency`, `DealProps.tla`): a deal is won at most once (its win is
  audited at most once), a won deal carries its win audit, a won deal never leaves Won, and the
  win write always ends. Run `strict` checks them for two deals and two callers with atomic
  steps, under a history bound (`BoundedSpec`: every effect but the win attempt and the win
  audit at most once per deal), and reaches a won deal and a lost and reopened one. Run `race`
  takes the row lock away (`Atomic: false`) and finds the double win: the trace
  `traces/deal-win.race.trace.json` and the obligation `cx:deal-win:race`.
- `record-ownership` (Alloy, `structure`, `crm_props.als`): the write policy as relations over
  the generated signatures, and assertions that every Deal has one owner, every Task one Deal
  and one assignee, nobody but the owner or an Admin writes a Deal, nobody but the assignee or
  an Admin writes a Task, and only an Admin reopens.

Every property has a mutation it must catch (10, all detected), and every assumption is proven:
`deal-win` A1 (a transition is one read-check-write under the row lock) by `cx:deal-win:race`,
A2 (the win write ends) by the induced timeout case `tc:DEAL-55eecd`; the three
`record-ownership` assumptions (the service's guards decide as the relations do) by the
ownership invariants the adversary tests prove.

`e2e/replay_test.go` replays the race trace against the real service: for 60 rounds it creates
a qualified deal, holds its row from an admin transaction until both win requests (the owner and
an Admin, as the trace's two callers) wait on it, then lets them go. Each round must end with one
200, one 409, one win audit row and one `deal_wins` row. The receipt for `cx:deal-win:race` says
`replay: refuted`; a double win would say `reproduced` and fail the suite. With the row lock
removed by hand (`FOR UPDATE` dropped from `LockDeal`) the second win is no longer a 409 but a
503 (the primary key of `deal_wins` and the single-writer trigger still keep a second win out),
which the test also rejects.

## The planner's loop

`make demo-pm` runs `demo/pm.sh`: it copies the committed tree into a temporary directory, makes
it its own git repository and its own bd backlog, then plays the planner (a new scenario and a
new abuse case, `machinery gen`, one suite run, `machinery owed sync`, `plan --apply`, `waves`,
`waves --freeze`, briefs for the builder, the verifier and the modeler of the critical story) and the gates (a consequential story and a critical one, proof by
`builder`, prediction and verdict by `verifier`, the builder refused as its own verifier). It
prints every command, stops at the first unexpected failure and removes the copy.

## Single writer

The engine keeps the service's own transition path on the table; the database keeps every other
code path off the state columns. `0006_single_writer.sql` adds `lifecycle_edges` and a trigger
on `deals.stage` and `tasks.status` that applies to the app role `crm_app` only. At start the
service replaces `lifecycle_edges` with the initial states and the persisted edges of the tables
it loaded (`fsm.Machine.PersistedEdges`: a transition into a transient state such as `closing`
is followed to the domain states it can end in). The save functions set `crm.transition` to the
fired case id in the same transaction, immediately before the update.

What it guarantees: as `crm_app`, a record is created only in its initial state, and its state
changes only along an edge of its machine and only inside the transition path (with
`crm.transition` set). Anything else fails with an error starting `lifecycle:`.

What it does not: a forged `crm.transition` on an allowed edge passes. Guards are the engine's
job, and `machinery probe` checks that the service really drives its transitions through the
engine. The admin role is not restricted, which is how the tests arrange data.

## Clean up

`make down`. Afterwards `docker ps -a --filter name=machinery-crm` prints no container.
